Engineering Solutions and Evaluating Trade Offs

My coursework developed my ability to connect a problem's requirements to its data structures and architecture. In the CS 300 Advising Assistance enhancement, course prerequisites became a directed graph rather than text attached to individual records. Hash-based lookup, an adjacency list, depth-first cycle detection, and topological sorting address different parts of the advising problem. I learned to explain why the relationships are represented in a particular direction and why a valid course sequence should be produced only after the catalog passes validation.

The enhanced catalog uses average O(1) hash lookup and performs alphabetical sorting when displaying the catalog. The DFS traversal takes O(V + E), where V represents courses and E represents prerequisite relationships; the full method also sorts vertices, making its expected bound O(V log V + E). The topological ordering uses a min-priority queue to make the result deterministic. That choice introduces a logarithmic heap cost compared with a standard queue, but makes output more reproducible for users and tests. Evaluating that trade-off strengthened my ability to consider usability and testability alongside asymptotic performance.

Software engineering coursework also showed me how responsibilities interact across an application. In Travlr Getaways, the interface, API, authentication logic, and database must agree on valid data and expected behavior. Centralizing validation and authentication middleware made those boundaries clearer. Correcting the Angular login flow reinforced the importance of connecting navigation to the actual asynchronous response. These experiences prepared me to investigate failures across layers instead of treating each component as an isolated program.

Enhancement One · CS 465

Travlr Getaways

A full-stack travel application originally developed in July and August 2026 and enhanced for CS 499 in September 2026.

Artifact and Selection

Travlr Getaways combines a public Express and Handlebars website with an Angular administrative application. A Node.js and Express REST API connects the interface to MongoDB through Mongoose. The application supports trip management and administrative authentication using Passport and JSON Web Tokens.

I selected this artifact because it demonstrates my ability to connect presentation, service, controller, model, and database layers. Enhancing the completed CS 465 Module Seven version allowed me to improve design and security across an entire application.

Design Improvements

I moved token verification into reusable authentication middleware and separated request validation and normalization from the controllers. Controllers now accept an explicit allowlist of trip fields. Trip codes are normalized consistently, duplicate codes receive a conflict response, and schema constraints reinforce validation. API errors avoid exposing internal exception details, and environment-specific configuration is managed through configurable values.

In Angular, I introduced a typed Trip interface, authentication guards for administrative routes, encoded trip codes in request URLs, and stronger form constraints. I also replaced a timer-based login check with a direct subscription to the HTTP observable. Navigation now follows a successful login response, and failures produce a clear error message.

Security Improvements

New passwords use a higher PBKDF2 work factor and constant-time comparisons. Compatibility with older user records is retained through a fallback for the original work factor. Tokens have a shorter configurable lifetime and enforce algorithm, issuer, and audience constraints. General login failure messages reduce disclosure of account information. Server-side authentication protects write operations, while client-side guards support the administrative user experience.

The completed application uses authentication-based write protection. Separate administrator/editor roles and audit records from the original plan were not implemented. Registration remains public, and registered users can obtain write-capable tokens. Trusted enrollment and role permissions remain future security work.

Learning and Challenges

This enhancement reinforced that working functionality also needs clear boundaries, predictable failure behavior, and maintainable structure. Separating validation and authentication showed me how middleware can establish a consistent boundary between untrusted requests and application logic.

Maintaining compatibility was a significant challenge. The password enhancement needed to preserve existing accounts, and price normalization needed to accommodate the original string-based dataset and numeric values from Angular forms. The login correction also strengthened my understanding of lazy observables and the need to connect asynchronous control flow directly to the operation.

Validation and Course Outcomes

The final backend run passes 38 tests, including HTTP authentication, protected writes, login behavior, password compatibility, and sanitized failures. Real Express routes, Passport, JWT, and password logic are exercised with Mongoose persistence stubbed. This is not live-database or browser end-to-end verification. Earlier milestone verification included JavaScript syntax checks, dependency installation, and a successful Angular production build. The build reported a non-failing warning that the initial bundle was approximately 50 KB above its configured budget, identifying a future optimization opportunity.

The narrative and technical documentation support Outcome Two, while compatibility decisions and validation trade-offs support Outcome Three. Enhancement Two · CS 300

Advising Assistance Program

Artifact and Selection

I created this C++ course-planning application in CS 300 Data Structures and Algorithms in June 2025 and enhanced it for CS 499 in September 2026. The original program loaded comma-separated course records, displayed an alphabetical catalog, and supported course searches with prerequisite information.

I selected this artifact because it demonstrates my progression from storing individual records to modeling connected dependencies. The original program treated prerequisites primarily as attached text. A directed graph makes it possible to validate those relationships and generate a prerequisite-respecting course sequence.

Algorithms and Data Structure Improvements

The enhanced CourseCatalog class replaces the global ordered map with an unordered_map keyed by normalized course number, providing average O(1) insertion and lookup. An adjacency list stores edges from prerequisites to dependent courses, and an in-degree map tracks each course's prerequisite count. Alphabetical display copies courses and their prerequisites before sorting, with O(V + E) copying and O(V log V) comparisons. Graph construction also sorts dependent lists. These costs make the implementation trade-offs explicit.

DFS traversal detects cycles in O(V + E), but this implementation sorts vertices first, so the complete method is expected O(V log V + E). It reports the actual circular chain. Kahn's topological-sort algorithm generates a valid completion sequence. A min-priority queue provides deterministic selection when multiple courses are available, with an expected bound of O(E + V log V). I accepted the heap cost because consistent results improve usability and testability.

The loader parses quoted fields, normalizes identifiers, and rejects malformed records, duplicate courses, repeated or missing prerequisites, empty datasets, and cycles. It builds and validates a candidate catalog before committing it, preventing partially loaded data from influencing advising results. Strict whole-line menu parsing allows the program to recover from invalid input.

Learning and Challenges

Modeling edge direction was an important challenge. Although a record lists its prerequisites, scheduling needs edges from each prerequisite to its dependent course so that completing a prerequisite reduces the dependent course's in-degree. This taught me to align stored relationships with the operation being performed.

Hash-table iteration also required careful handling because its unspecified order could produce inconsistent output. Sorting for display and using a min-priority queue for scheduling resolved that issue. Transactional loading taught me that rejecting a bad record is insufficient if earlier records have already changed active state. These decisions connect with my human-computer interaction interests through predictable output and specific error messages.

Validation and Course Outcomes

All ten regression tests passed under the warning-enabled build and with AddressSanitizer and UndefinedBehaviorSanitizer; leak detection was disabled because of the execution environment. Leak checking was not completed. Coverage includes loading, normalized lookup, alphabetical display, topological ordering, quoted titles, duplicates, missing prerequisites, cycles, malformed or empty data, and invalid menus.

Outcome Three is the primary focus through graph modeling, algorithm selection, complexity analysis, and explicit trade-offs. The working application supports Outcome Four; documentation and clear feedback support Outcome Two; defensive parsing and rejection of inconsistent input support Outcome Five. Documentation provides limited support for Outcome One, which is discussed through coursework examples in the professional self-assessment.

Instructor Feedback Follow Up

Twelve generated graph configurations passed, including sparse, chain, and wide cases up to 4,000 courses and dense cases up to 499,500 edges. Each configuration ran three times. Every prerequisite was checked against the output order, repeated schedules had to match, and a separate 4,000-course cycle was rejected. These local timings describe synthetic inputs, not production guarantees.

Enhancement Three · CS 340

Grazioso Salvare Rescue Animal Dashboard

Artifact and Selection

This CS 340 Client/Server Development artifact connects a Python dashboard to MongoDB shelter records through an AnimalShelter CRUD module. The original notebook includes an animal table, breed chart, location map, and rescue-category filters. Its supplied source archive is dated February 22, 2026; that date identifies the archive rather than establishing the exact creation date. I enhanced the project for CS 499 in October 2026.

I selected this artifact because database design directly affects the reliability of rescue-planning information. The enhancement demonstrates secure data access, schema validation, controlled queries, pagination, aggregation, and measured index evaluation.

Database and Security Improvements

Python validation checks required fields, permitted values, text lengths, finite numbers, and coordinate ranges. It rejects unsupported fields, MongoDB operators, and caller-controlled audit metadata. MongoDB also enforces a strict JSON Schema validator. A migration preflight checks historical records and stops when invalid data requires attention.

Environment variables replace embedded connection configuration. Authenticated, collection-scoped reader and editor roles enforce viewing and writing permissions in MongoDB. Updates and deletes target a single record ID. Creation and modification metadata capture the database account and timestamp, while atomic soft deletion preserves deletion metadata. This metadata is not an immutable audit ledger, and a shared account does not identify individual people.

Server-side pagination bounds page size at 100 and uses _id as a deterministic sorting tie-breaker. The dashboard requests ten records per page. Breed aggregation covers all matching records, preserving the distinction between a displayed page and the complete results. A separate $facet pipeline summarizes rescue categories while retaining category overlaps. The browser remains read-only; editor CRUD operations are available through the service.

Validation and Performance Evidence

All 22 integration tests passed against an authenticated MongoDB 8.0.12 instance. They cover CRUD, audit metadata, soft deletion, schema enforcement through direct writes, invalid inputs, operator rejection, reader write denial, collection permissions, pagination, aggregation, migration, and dashboard callbacks.

An executionStats comparison used 30,000 synthetic AAC-like records containing 300 water-rescue matches. After indexing, documents examined fell from 30,000 to 300, a 99 percent reduction, while the first ten result identities remained unchanged. A sort stage remained for animal-ID ordering. These results describe the test workload, not guaranteed production performance.

Indexes introduce storage and write overhead. Deep offset pagination becomes more expensive, and separate page and count queries can differ during concurrent writes. The original shelter dataset was unavailable, so migration against that dataset remains a future verification step.

Learning and Challenges

Server-side pagination required changes to the dashboard callback contract and revealed that a chart based only on the current page could misrepresent the dataset. Aggregation solved that problem while keeping table requests bounded. Historical compatibility required preserving original field names and screening rules and avoiding an unsupported unique constraint on animal IDs.

Testing both the service and direct database access reinforced that authorization must hold when application checks are bypassed. Evaluating actual query plans also taught me to distinguish measured improvements from assumptions. This work connects secure backend design with a clearer interface, supporting my full-stack and human-computer interaction interests.

Course Outcome Progress

Outcome Four has the strongest evidence through the MongoDB and Python solution. Database-enforced least privilege and controlled writes support Outcome Five. Query plans, stable results, and performance trade-offs support Outcome Three. The narrative, README, interface labels, and reproducible evidence support Outcome Two. Documentation helps maintainers and rescue staff interpret results, but this individual project does not establish completion of a collaborative team process or evaluation with diverse users.
